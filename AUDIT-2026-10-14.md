## HIGH

### H1. Secrets flagged as compromised appear never to have been rotated

`SECURITY.md` states the following were exposed in git history and "**must be rotated** on first deploy": `RECAPTCHA_SECRET_KEY`, `RESEND_API_KEY`, `SANITY_API_WRITE_TOKEN`, `SANITY_REVALIDATE_SECRET`, `DATABASE_URI`, `CLOUDINARY_API_SECRET`, `PAYLOAD_SECRET`, `JWT_SECRET`, and all admin passwords.

Evidence rotation did **not** happen: `SANITY_REVALIDATE_SECRET` in `.env.local` is still a 32-character human-readable passphrase beginning `my-su…` — not a generated random secret. That is the shared secret guarding `/api/revalidate`; it is guessable.

Current git history is clean (only `.env.example` placeholders), so the history was rewritten — but **rewriting history does not un-leak a secret**. Anyone who cloned or forked before the rewrite still holds them.

**Fix:** rotate all nine, treating every one as burned. Generate the revalidate secret properly:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

### H2. Nine unused secrets sit in `.env.local` for systems this app does not use

Cross-referencing every `process.env.*` reference in `src/`, only 12 variables are actually read. These are present but **never used anywhere in the codebase**:

`SANITY_API_WRITE_TOKEN` (a **write** token to your production dataset), `DATABASE_URI` (Neon Postgres credentials), `PAYLOAD_SECRET`, `JWT_SECRET`, `CLOUDINARY_API_SECRET` / `_API_KEY` / `_CLOUD_NAME`, `ADMIN_USER_*`, `SEO_USER_*`, `ADS_USER_*` (PBKDF2 hashes + salts), `NEXT_PUBLIC_SERVER_URL`.

This is leftover Payload-CMS/Cloudinary scaffolding. Each is attack surface with zero benefit — a leaked `SANITY_API_WRITE_TOKEN` means an attacker rewrites your live blog content.

**Fix:** delete them from `.env.local`, `.env.example`, and the Vercel dashboard. Revoke the Sanity write token and the Neon credentials at the source.

### H3. Booking-form rate limiting does not work in production

`src/app/api/book/route.ts:28-50` — three independent defects:

1. **In-memory `Map` on serverless.** Vercel runs each request in a lambda that may be a cold instance. The counter resets constantly and is not shared across concurrent instances, so the "5 per 15 min" limit is effectively unenforced under any real load.
2. **Unbounded memory growth.** `ipRequestMap` is never pruned — expired entries are only overwritten if that exact IP returns. A spray of unique IPs grows the map until the instance OOMs.
3. **Spoofable IP source.** `getClientIp()` (line 73) falls back to `cf-connecting-ip`, a header the client fully controls when you are not behind Cloudflare. An attacker sends a random `cf-connecting-ip` per request and gets a fresh bucket every time.

**Fix:** move to a shared store — `@upstash/ratelimit` with Vercel KV, or Vercel's built-in WAF rate limiting. Trust only `x-vercel-ip-address` on Vercel; drop the `cf-connecting-ip` branch unless Cloudflare actually fronts the site.

### H4. Production CRM webhook URL is hardcoded in source

`src/app/api/book/route.ts:89-90`:

```ts
const DEFAULT_PABBLY_WEBHOOK_URL =
  'https://connect.pabbly.com/webhook-listener/webhook/IjU3NjMwNTZmMDYzNTA0M2Q1MjZjNTUzNiI_3D_pc/...';
```

This committed URL is an unauthenticated ingestion endpoint for your sales pipeline. Anyone with repo access — or anyone who finds it in a fork or clone — can inject unlimited fake leads directly into Pabbly, bypassing your site, your rate limit and your reCAPTCHA entirely.

**Fix:** delete the constant, read `process.env.PABBLY_WEBHOOK_URL` only, and regenerate the webhook URL in Pabbly since this one is burned.

### H5. reCAPTCHA fails open in three separate ways

Same file, lines 170-205:

- **Network error → request accepted.** The `catch` around `siteverify` only logs (line 199); execution falls straight through to sending the email. An attacker who can make Google's endpoint slow or unreachable — or simply retries until one call times out — bypasses the captcha.
- **Missing secret → verification skipped.** If `RECAPTCHA_SECRET_KEY` is unset in production, it logs a warning and continues (line 176).
- **No `hostname` check.** `verifyData.success` is checked but `verifyData.hostname` is not, so a token minted on any other property using the same site key is accepted.

**Fix:** on any verification failure *or* exception in production, return 400. Assert `verifyData.hostname === 'halatechnology.ae'`. Make a missing secret a hard 500 rather than a skip.

### H6. `public/robots.txt` silently overrides `src/app/robots.ts`

Both exist. Static files in `public/` are served before App Router routes, so the generated version **never reaches crawlers**.

- `src/app/robots.ts` disallows `/api/` and `/studio/`.
- `public/robots.txt` — the one actually served — says only `User-agent: *` / `Allow: /`.

Net effect: your Sanity Studio login and all API routes are open to crawling and indexing.

**Fix:** delete `public/robots.txt`. The route handler already produces the correct output (confirmed in the build as `○ /robots.txt`).

### H7. Four pages declare the homepage as their canonical URL

`src/app/layout.tsx:69` sets `alternates: { canonical: BASE_URL }` on the root layout. Any page that does not override it inherits it. Verified in the built HTML:

```
.next/server/app/privacy-policy.html        → <link rel="canonical" href="https://halatechnology.ae"/>
.next/server/app/faqs.html                  → <link rel="canonical" href="https://halatechnology.ae"/>
.next/server/app/cookie-policy.html         → <link rel="canonical" href="https://halatechnology.ae"/>
.next/server/app/terms-and-conditions.html  → <link rel="canonical" href="https://halatechnology.ae"/>
```

All four tell Google "I am a duplicate of the homepage," which is a direct instruction to drop them from the index. `/faqs` in particular is content you want ranking.

**Fix:** add the correct `alternates.canonical` to each of the four pages. Better: remove `alternates` from the root layout entirely so a missing canonical can never silently become the homepage.

## MEDIUM

### M1. The production CSP will break Sanity Studio

The header rule `source: '/:path*'` applies the CSP to `/studio` too (confirmed in `routes-manifest.json`). In production the policy drops `'unsafe-eval'` and specifies no `worker-src`. Sanity Studio requires both — it evaluates GROQ dynamically and runs web workers from `blob:`.

**Fix:** add a `/studio/:path*` header rule that relaxes the policy for that path only — `script-src` with `'unsafe-eval'`, plus `worker-src 'self' blob:` — and leave the strict policy on the public site. Verify by loading `/studio` on production and checking the console for CSP violations.

### M2. Body-size guard runs *after* the whole body is read

`route.ts:131-140` checks `content-length`, but a missing or lying header passes (`Number(null)` is `0`), and the real check happens only after `await request.text()` has already buffered the entire payload into memory. A 500 MB POST is fully read before being rejected.

**Fix:** stream and abort past the limit, or enforce the cap at the edge (Vercel WAF or `middleware.ts`).

### M3. Blog 404 path triggers a full-collection scan — DoS amplification

`src/app/blogs/[slug]/page.tsx:40-52`: when a slug does not match, the fallback fetches **every post slug in the dataset** (`allPostSlugsQuery`), matches in memory, then issues a second fetch. With `useCdn: false` (see M4) all of it hits the uncached Sanity API.

Since `dynamicParams = true`, a bot requesting `/blogs/<random>` in a loop drives two uncached full-collection queries per request against your Sanity quota.

**Fix:** cache the slug map (`unstable_cache` / `revalidate`), or drop the fallback and rely on the 301 redirects already in `next.config.mjs`.

### M4. `useCdn: false` disables Sanity's CDN on every query

`src/sanity/lib/client.ts` via `src/sanity/env.ts:14`. Every blog page, the blogs index, `LatestBlogsSection` and `sitemap.ts` go to the live API instead of the edge cache — slower and far more expensive. With `perspective: 'published'` and ISR at 60s there is no freshness argument for it; the `/api/revalidate` webhook already handles invalidation.

**Fix:** set `useCdn: true`.

### M5. Studio layout nests a second `<html>`/`<body>`

`src/app/studio/[[...tool]]/layout.tsx` renders `<html><body>` — but it is a *nested* layout under `src/app/layout.tsx`, which already renders them. Output is `<html><body>…<html><body>`: invalid HTML and a hydration mismatch.

**Fix:** move the studio into a route group with its own root layout (`src/app/(studio)/studio/[[...tool]]/`) and strip `<html>`/`<body>` from the nested one.

### M6. Sentry is fully configured but captures nothing

- `NEXT_PUBLIC_SENTRY_DSN` is **absent from `.env.local`** → `Sentry.init()` is a no-op.
- There is **no `instrumentation.ts` and no `instrumentation-client.ts`**. Sentry v10 + Next 16 load client/server config from those files; the legacy `sentry.client.config.ts` / `sentry.server.config.ts` are no longer read.
- Confirmation: `tunnelRoute: "/monitoring"` produces **no rewrite** in the built `routes-manifest.json`.

You are paying the build cost and carrying the dependency while having zero error visibility on a production site.

**Fix:** either wire it properly (set the DSN, create `instrumentation.ts` + `instrumentation-client.ts` per Sentry's Next 16 guide) or remove `@sentry/nextjs` and `withSentryConfig`. Also drop `transpileClientSDK` (removed in Sentry v9+) and lower `tracesSampleRate` from `1` to roughly `0.1`.

### M7. The cookie banner is cosmetic — no tracker is actually gated

`src/components/CookieBanner/CookieBanner.tsx` writes `hala_cookie_consent` to `localStorage` and hides itself. Nothing reads that value. Meanwhile `src/app/layout.tsx` loads GTM (line 83), HubSpot (line 124), LeadConnector tracking (line 131), Vercel Analytics and Speed Insights — **unconditionally, before any choice is made**.

Clicking "Decline" changes nothing. For a UAE agency with EU-facing clients this is a GDPR/PDPL exposure, and it misrepresents your own privacy policy.

**Fix:** implement Google Consent Mode v2 — set `default` consent to `denied` in a `beforeInteractive` script, then `gtag('consent','update',…)` on Accept. Gate the HubSpot and LeadConnector `<Script>` tags behind consent state.

### M8. Structured data never reaches the initial HTML

All JSON-LD (`LocalBusinessSchema`, `ServiceSchema`, blog `BlogPosting`) uses `next/script`, which defaults to `afterInteractive` — injected client-side after hydration. Verified in the build: the homepage HTML contains no `<script type="application/ld+json">` tag, only a serialized component inside the RSC flight payload.

Googlebot renders JS and will usually catch it on the second pass, but Bing, social validators, raw-HTML rich-results checks and LLM crawlers will not. For an agency selling SEO, this is worth fixing.

**Fix:** replace `<Script type="application/ld+json">` with a plain JSX `<script type="application/ld+json">`.

> **Important coupling:** `JSON.stringify()` does **not** escape `<`. Today that is inert because the payload sits inside a JS string. The moment you make the fix above, a Sanity post titled `</script><img src=x onerror=…>` becomes **stored XSS** — `blogs/[slug]/page.tsx:225` interpolates `post.title` and `post.authorName` straight from the CMS. Apply both changes together:
>
> ```ts
> __html: JSON.stringify(schema).replace(/</g, '\\u003c')
> ```

### M9. Image optimizer accepts wildcard remote hosts

`next.config.mjs` `remotePatterns` allows `*.filesafe.space` and `*.highlevelcontent.com` with no `pathname` restriction. Combined with the unpatched SSRF advisory in C1, any subdomain an attacker controls under those zones can be proxied through `/_next/image` — using your bandwidth and your server's network position.

**Fix:** pin exact hostnames and add `pathname` constraints. `i.pravatar.cc` and `images.unsplash.com` look like leftover placeholder hosts — remove them if unused.
